# Sandbox operation fencing — candidate protocol

Status: reference design only. The test model assumes atomic storage behavior; no current repository, reset adapter or MySQL server enforces this protocol. Do not enable visitors on this evidence.

## Threat model for this stage

The user selected trusted backend processes: protect against implementation errors, delayed requests, concurrency and process failure. Under this assumption, visitor isolation and reset fencing are still required and must be verified before enabling the demo. A compromised backend process or stolen runtime credential may bypass application-enforced fencing and is outside this lease-isolation guarantee. Per-slot least-privilege credentials are still desirable to reduce blast radius, but do not isolate successive leases of the same slot. This decision does not authorize real grants, routes or database access.

## Safety target

No operation from an old lease may read or write a slot while reset is running or after a new lease becomes active. The existing control-plane lease check alone cannot enforce this across independently committed slot transactions. An operation admitted before expiry may finish before the fence is established; the protocol must not claim instantaneous cancellation at the expiry timestamp.

## Candidate storage protocol

The slot database needs a durable fence record, outside the data reset deletes, containing the current lease, generation and open/fenced state. Each slot operation, including reads, holds a shared lock on that record for its entire database transaction, checks the lease and generation under the lock, and performs all slot access in that same transaction. The reset worker takes an exclusive lock on the same record, waiting for already-admitted transactions to finish, then closes admission and persists the reset attempt. A paused operation that has not acquired the lock must check again after it acquires it. Transactions must never escape the lock through another connection or nontransactional table.

Reset and verification are performed only after fencing. All data-plane reset effects must themselves be fenced against stale reset attempts; a control-plane completion CAS alone is insufficient. This may require a separate storage-level reset mechanism if reset uses DDL or external effects that cannot be held inside the same transaction. Do not assume a SQL row lock covers such effects.

A new lease is admitted only after verified reset and explicit reconciliation of the slot fence and control plane. Their commits are not atomic: every intermediate state and restart must fail closed; an uncertain outcome must not release or reuse the slot. The exact activation ordering, durable recovery protocol, reset adapter and transactional coverage remain design obligations, not implemented facts.

## Cross-plane activation: abstract model

The reference activation model proposes control states `closed → reserved → active` and slot states `fenced → prepared → open`, in that order, with the same lease identity. New lease reservations require closed/fenced; access requires active/open and matching identity. An interrupted activation is reconciled by fencing the slot and quarantining it, not by automatically opening or reassigning it. Recovery requires confirmation that the previous worker stopped. Reopening after recovery requires a separate verified reset and allocation; that transition is intentionally not modeled.

The model represents an interruption with a global `interrupted` flag. **This is an oracle, not a real crash detector or distributed lock**: in the real system another process cannot rely on immediately observing a crash. It also assumes atomic, durable transitions, an exclusive slot fence that waits for active transactions, and serialization of control-plane expiry/reallocation with every activation step. In particular, an old activation worker must not be able to open the slot after its authority is lost; checking the control plane before writing to a different database does not by itself establish that. The storage-enforced authority, uncertain commit resolution, timeout and cross-plane ordering are still unimplemented design obligations. The model's green tests do not prove a realizable distributed protocol.

## Alternative: one server transaction for control and slot fence

The accepted topology assumes the control database and slot databases are on one MySQL server, but the slot connection factory does not configure or verify the control-plane endpoint. A candidate alternative is to update the control lease and that slot's fence as InnoDB DML in **one transaction on one connection**, using qualified table names. This could remove the two-commit activation window for those rows, rather than coordinating two independent commits. It is a design hypothesis, not an implementation or proof: the configured endpoint has not been contacted, server/version/engine and schema names have not been verified, and permissions must permit both accesses on the same session.

The current factory instead uses a separate account and Sequelize instance per slot. A connection capable of accessing the control plane and a slot would change its trust boundary. Granting a slot account access to a shared control table may expose or modify other slots; a coordinator account able to access multiple slot databases may undermine account isolation. Database-level grants do not by themselves establish row-level isolation. Do not grant either permission or choose an account architecture without a separate security design and explicit authorization.

Within this candidate, slot operations still require same-transaction storage-enforced lease/generation checks. A control+slot transition must use lock ordering consistently and fail closed on timeout/deadlock; ambiguous commit must be resolved from durable state, never guessed. Reset DDL or external effects remain outside this DML transaction: MySQL documents that many DDL statements cause implicit commits, so they cannot safely be assumed to retain the fence lock. Reset-worker fencing, restart and verification still require an explicit protocol.

Reference documentation (MySQL 8.0; actual server version unknown): [transaction statements](https://dev.mysql.com/doc/refman/8.0/en/commit.html), [locking reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html), and [implicit commits](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html). These sources describe mechanisms, not this application's guarantees. The existing separate-commit reference model does not implement or test this alternative.

## Candidate roles and reset sequence

This is a least-privilege **target**, not an approved grant list or implementation. Exact privileges, authentication, table engines, and whether MySQL can enforce the required separation are unresolved. A process holding a credential can exercise all its grants: application-level selection of a slot does not constrain a compromised credential.

| Principal | Intended reach | Explicit exclusions and caveats |
| --- | --- | --- |
| Slot runtime | One slot's business tables and the minimum read/locking access to its fence | No other slot or control-plane business data; a fence permission must not permit runtime to rewrite it. Existing grants and locking-read privilege requirements are unverified. |
| Coordinator | Control lifecycle rows and each configured slot's fence only, using one session for cross-schema DML | No slot business-table data, production schemas, DDL, account or grant administration. Shared-table access is not row-level isolation; compromise could affect confidentiality and integrity as well as availability by publishing a dirty or attacker-selected lease. |
| Reset worker | Only the selected slot's resettable business data and fence for a bounded transactional reset | No other slot, production, account or grant administration. A broad worker credential changes the blast radius; per-slot restriction and required privileges need verification. |
| Operator | Provisioning and exceptional recovery | Separate from request-serving processes; no automatic recovery based solely on a timeout. |

Direct business-table grants alone cannot enforce the fence: a compromised or defective runtime can omit the lock, use another transaction or commit early. The selected trusted-backend boundary does not excuse a defective repository omitting the lock: implementation errors remain in scope. Fence coverage must be enforced by a suitable architecture and verified across every access path; per-slot accounts do not isolate successive visitors of one slot. Coordinator transition authority and reset receipt provenance likewise require enforcement, not just application checks.

The coordinator must not trust a caller-provided schema identifier; bind each operation to a validated operator-configured slot. The runtime, coordinator and reset worker require independently scoped credentials; storing them separately in the same process does not provide process-level compromise isolation. Whether the existing process topology can actually enforce this separation is open.

Candidate **DML-only** sequence, conditional on all affected tables using InnoDB and on demonstrated privileges and lock semantics:

1. In a single coordinator transaction, lock control row then slot fence in a fixed global order, validate lease/generation, move control to draining/resetting and fence the slot. Existing operations holding the slot fence finish before the exclusive fence is acquired. Commit both changes together. Timeout, deadlock or uncertain commit means no reset or reassignment until durable state is reconciled.
2. A slot-specific reset worker starts a transaction, takes the exclusive slot-fence lock, verifies the current durable reset attempt and generation under that lock, deletes/reseeds only approved transactional tables and verifies the result **inside the same transaction**. It holds the lock until commit or rollback; failure leaves admission fenced. Do not use DDL, `TRUNCATE`, nontransactional tables, external calls or any other implicit-commit operation in this transaction.
3. Only after a durable, attempt-bound verification result is available may the coordinator, in one cross-schema transaction and with the same lock order, confirm the attempt, advance generation and publish the next admissible state. A durable receipt must bind slot, generation, reset attempt and reset/seed version, with restricted issuer and consumption rules; the issuer's authority, persistence, stale-receipt rejection and activation timing remain to be specified. A stale worker must not be able to write, verify, or publish after authority changes.
4. If a worker or connection is lost, leave the slot unavailable. Resolve ambiguous commits from durable state. Operator-mediated recovery requires confirmation that the old worker stopped and any database transaction has ended, a fresh non-reusable attempt, a repeated reset and verification; no timed assumption that a paused worker is dead.

This sequence depends on MySQL lock ordering and privilege semantics not yet checked against a real deployment. The reset worker may not be able to persist its verification evidence with the proposed grants; cross-schema privilege design must address that explicitly. If any reset effect cannot participate in the transaction, or a worker can still execute after its lock is lost, the sequence is insufficient and the slot must remain unavailable. Existing `ResetDemoSandboxSlotUseCase` only fences control-plane completion; it does not implement these steps.

## Candidate receipt and ambiguous-commit recovery

Under the selected trusted-process model, the reset transaction would lock the slot fence, check its current generation and non-reusable attempt ID, reset and verify the approved transactional data, then insert a receipt **in the same slot transaction**. The receipt records slot, generation, attempt, reset/seed version and verification result. A receipt must not be inferred from a returned success, a timestamp, or a separately committed verification. The fence and receipt must survive reset; receipt history/uniqueness and identity generation need a durable design.

The coordinator may release a slot only while holding control then fence locks in one transaction and after checking an exact successful receipt for the current generation, attempt and expected reset/seed version. The release predicate must match control and fence slot, phase, generation and attempt, as well as the exact expected version and an unconsumed successful receipt. It consumes that receipt and advances the durable generation/fence and control state together; stale, missing, mismatched or already-consumed receipts reject release. The worker must never acquire the control lock while holding the slot lock. Every other lifecycle path needs an audited compatible order; this is a design requirement, not an existing property.

| Uncertain event | Conservative recovery candidate |
| --- | --- |
| Fence transition acknowledgement lost | Re-read authoritative durable control and fence state before any reset; mismatched or unreadable state stays unavailable. |
| Reset commit acknowledgement lost | Wait until the prior transaction ended; read the exact receipt and fence under the required locks. If exact receipt exists, proceed to guarded release; if absent, require stopped-worker confirmation and a new fenced reset attempt. Never assume a timeout means rollback. |
| Recovery-claim acknowledgement lost | Re-read both authoritative locked rows in a fresh transaction, including old and replacement attempt IDs. Identify the winner durably; if unreadable or inconsistent, remain unavailable. Never assume rollback, run reset or generate another claim from a timeout alone. |
| Release commit acknowledgement lost | Re-read control, fence, generation and receipt consumption as one consistent authoritative snapshot before any retry or allocation; ambiguous, stale-replica or inconsistent reads leave the slot unavailable. |

Worker admission must also require the exact closed/resetting fence state and reject duplicate successful or consumed attempts before any reset effects. Competing recoveries need an atomic durable claim/CAS, and all later actions must revalidate the winning attempt under lock. Fresh-transaction and database isolation/snapshot rules must prevent a read begun before fencing from observing an old snapshot after reassignment. Candidate rules follow below; none is implemented or demonstrated.

The required authoritative-read, durability and failover semantics, stable seed version, ID non-reuse, receipt issuer, exact SQL/privileges and exhaustive lifecycle lock ordering remain unverified. A committed receipt does not by itself prove correct reset data or MySQL durability. The current reference models do not model this sequence, and the existing reset port returns only a Boolean. No rollout or real DB access is authorized by this proposal.

## Receipt and identity storage proposal (not executable DDL)

Keep the following append-only records outside every resettable table, subject to a separately reviewed retention and restoration policy. The physical types, character set, collation, engine and server version are not yet validated. No table or migration for this proposal exists.

- **Lease identity history:** unique lease identity and its slot/generation; allocation inserts the identity in the same coordinator transaction that changes control and fence. Never recycle an identity, including after reset, backup restoration or slot reprovisioning. Restore and disaster-recovery procedures must preserve this invariant or invalidate the entire affected identity namespace.
- **Reset attempt history:** unique attempt identity bound to slot and generation, recorded atomically with the durable claim. Replacement is a new insertion plus compare-and-swap of the current authority under control-then-fence locks, never deletion or reuse of an earlier identity. Unknown transaction outcome requires authoritative reconciliation before a new claim.
- **Successful reset receipt:** immutable slot, generation, attempt and seed-version identity, with uniqueness at least on attempt identity independently of version and consumption state. Record only after reset and verification in their slot transaction while holding the exclusive fence. Receipt history must survive reset and stay associated with attempt history. Record provenance and issuer authorization remain unresolved.
- **Consumption:** an initially unconsumed receipt is consumed once by the coordinator in the same transaction that validates both lifecycle rows and publishes the next state. A conditional update, retained consumed state and a unique durable receipt prevent replay only if enforced in the actual database and all transitions use them. A read followed by an unguarded later update is insufficient.

No retry or release follows an ambiguous commit until the original transaction is known ended and an authoritative, fresh, consistent read reconciles the exact attempt, receipt and control/fence state. A missing or inconsistent result is not proof of rollback or reset correctness. Server failover durability, role grants, namespacing, actual schema and recovery from lost history remain unresolved; this proposal is not executable and does not authorize MySQL access.

`RunFencedSandboxReset` is an isolated orchestration seam: it orders fence, receipt existence, reset, verification and insertion in a supplied unit of work. `DemoSandboxResetReceipt` declares an attempt primary key, `SequelizeSandboxReceiptWriter` provides slot-bound lookup and insertion, and `20261103000000-demo-sandbox-reset-receipt.js` provides its isolated slot migration source (outside the control migrator glob, unexecuted). This declaration and schema can at most constrain attempts within one slot database; globally non-reusable identity history, collation/UUID semantics, restoration and cross-slot reuse remain unresolved. The writer does not itself acquire a reset fence: the caller must retain an exclusive lock and all operations must stay transaction-bound. No receipt runner, reset DML, or release gate is deployed. Mocks cannot establish rollback, SQL uniqueness, lock retention or durable storage.

## Isolated single-transaction release seam

`ReleaseSandboxInTransaction` is unwired orchestration over abstract ports: it asks for the control lock and validation first, then the fence lock and validation, then consumes the exact receipt and finally requests a joint control/fence release in the same supplied context. A rejected final transition throws inside the unit-of-work callback, so a correctly implemented transactional unit of work can roll back the receipt consumption. Any exception, including a potentially ambiguous commit, yields `uncertain` and requires authoritative reconciliation; it must not trigger an automatic retry.

The ports and mocks do not enforce a real transaction, lock acquisition, model binding, correct state predicates, jointly updated rows or rollback. No adapter implementing these new release ports exists. The earlier `ReleaseFencedSandboxSlot` uses two transactions and must not be wired to visitors. Real same-server topology, grants, engine, isolation, durable identity and receipt provenance remain prerequisites; no MySQL test is authorized by this design.

## Proposed rules for the four remaining gaps

These are proposed acceptance rules, not implemented mechanisms or a complete proof:

1. **Worker replay:** after taking the exclusive slot fence, the worker checks `resetting`, slot ID, generation, current attempt and expected seed version, and checks there is no successful or consumed receipt for that attempt. Mismatch or existing receipt means rollback before any reset effect. A concurrent duplicate waits for the fence, then rechecks. A failed transaction may be retried only after its outcome is known; an uncertain outcome follows the receipt-reconciliation table above. Unique durable receipt identity must be enforced by storage, not an in-memory set.
2. **Competing recovery:** a recovery coordinator first establishes that the earlier worker and its transaction have stopped, then atomically claims recovery under control-then-fence locks, conditional on the exact old generation and attempt and the still-closed resetting state. It replaces the attempt with a fresh non-reusable ID in both rows in the same transaction. Only one contender can win. Every worker and release rechecks the current attempt under its respective lock; failed CAS, missing row, lock timeout, ambiguous commit or unavailable authority must not release the slot. Confirming a worker stopped is an operator assertion whose verification procedure is still unspecified.
3. **Snapshot freshness:** begin a fresh transaction on the slot's authoritative connection without transaction-start options that establish a snapshot; acquire and validate the fence as its first database operation before any consistent-read snapshot or business query. Test pooled-session and driver behavior. Keep the lock through every read/write and commit or rollback; reject already-started transactions, foreign connections and queries that escape the transaction. Isolation settings and driver behavior must be validated on the exact MySQL version; this rule alone is not proof that all isolation modes are safe.
4. **Complete coverage:** route all visitor-visible slot operations and slot-mutating jobs through a mandatory transaction boundary that acquires the fence before exposing repositories. Audit raw SQL, ORM calls, scheduled jobs, event handlers and reset/seed adapters; reject or quarantine any path without a proven boundary. Architecture checks and negative tests should detect bypasses, but are not a database security boundary and cannot prove no future bypass. The mechanism must reject repositories that omit or replace the transaction, foreign connections and detached work. Inventory, transaction ownership enforcement and concrete integration remain to be designed and tested.

A test plan must exercise duplicate workers and recovery claim races, interruption before and after each commit, old transactions/snapshots, timeouts, foreign transactions and each identified access path. It must distinguish simulation from real concurrent MySQL verification. Until those checks and the permission/reset obligations above are satisfied, no visitor-isolation claim is justified.

## Slot fence migration boundary

The isolated slot migration source uses a static MySQL `CREATE TABLE` without `IF NOT EXISTS`, so an existing table should produce an error rather than be silently accepted; mock tests assert the emitted statement and error propagation, not real MySQL behavior. A lost DDL acknowledgement may leave a table present without a recorded migration: do not automatically retry or adopt it. A separate operator reconciliation must inspect the authoritative schema and migration ledger; the required comparison and runner do not yet exist.

The five-column table is not a complete enforcement schema. In particular, it does not establish non-reusable lease or reset-attempt identities, receipt provenance, correct state/lease combinations, or atomic transitions with the control plane. A uniqueness index on a mutable current-attempt column alone cannot prevent reuse after its value changes. Define durable history and version-specific constraint enforcement before relying on these invariants. The file is outside the control-plane migrator glob and has no authorized real execution path.

## Failure boundaries

- An indefinitely held transaction can block the exclusive fence indefinitely. A timeout must leave the slot unavailable; cancellation or connection termination is not presumed to work across processes.
- Database crash, lock loss, worker crash, or ambiguous commit leaves the slot unavailable until durable state is reconciled. Recovery requires proof the previous reset worker stopped, plus fencing of its data-plane effects.
- A freshly allocated lease must use a new identity and next generation. Reset attempts also need non-reusable authority across recoveries and generations; immediate-predecessor comparison alone permits ABA. Previous tokens and operations must fail under the storage fence, not only at request entry. The model retains all prior identifiers in memory solely to express uniqueness; durable generation-bound authority and its retention strategy remain to be designed.
- External writes, background jobs, raw SQL, nontransactional tables, separate connections and reset DDL require explicit coverage; a single bypass invalidates the safety claim.
- Reads have the same generation check as writes to prevent cross-visitor disclosure.

## Reference model and proof limits

`backend/src/application/__tests__/support/demoSandboxFenceModel.ts` is a deterministic state model, not production code. Its atomic methods stand in for unimplemented storage semantics. Tests cover admitted-operation ordering, delayed old admission, stale or reused reset attempts, reused lease identities, and fail-closed activation. The model does not simulate network partitions, real transactions, isolation levels, DDL, process death or cross-database commits. Its success cannot establish the safety of a future implementation.

`backend/src/application/__tests__/support/demoSandboxActivationModel.ts` separately models control and slot state and a conservative interruption/reconciliation path. Its boolean interruption oracle and instantaneous cross-plane checks are assumptions, not MySQL or distributed-system behavior. The tests enumerate interruption at each modeled step, not all possible concurrent schedules or ambiguous commits.

`backend/src/application/__tests__/support/demoSandboxReceiptModel.ts` models exact receipt identity, duplicate successful reset rejection and single consumption. Each method assumes atomic serialized durable storage and successful verification: it does not implement durable receipts, lifecycle phases, locking, recovery, generation advancement or real reset effects. Tests do not cover every reset-admission identity mismatch or reset after receipt consumption. This simulation provides no MySQL or visitor-isolation proof.

Before implementation, validate the protocol against the actual MySQL version, reset strategy, all repository paths and permissions. Before enabling visitors, separately authorize a disposable MySQL host/schema and run concurrency, crash/recovery and isolation checks there.
