## Exploration: deploy-topology

### Current State

**Boot sequence (`backend/index.js`)**: fail-closed and migration-aware already. Sequence: `ensureDatabaseExists(env)` → `db.sequelize.authenticate()` → `checkNoPendingMigrations()` → `seedInitialData(db)` → `.listen()` → `markReady()`. Boot never calls `sequelize.sync({ alter: true })` (locked in by `openspec/specs/schema-migrations/spec.md`). `RUN_COMPILED=true` (deliberately independent of `NODE_ENV`) makes `index.js`/`app.js` require from `./dist` instead of `./src`, skipping `ts-node/register` — the "compiled production entry point" decision referenced in code comments. The original `design.md` that coined this decision is not findable anywhere in the current tree (only comment references survive, likely from an already-archived SDD change). Graceful shutdown on `SIGTERM`/`SIGINT`: flips readiness unready immediately, stops new connections, drains in-flight requests, closes Sequelize, force-exits after `SHUTDOWN_TIMEOUT_MS` (default 10000ms, env-tunable). A signal before `.listen()` resolves aborts boot with exit code 1. All spec-locked in `openspec/specs/runtime-resilience/spec.md`.

**Readiness** (`backend/src/infrastructure/health/readinessState.ts`): trivial in-memory latch (`markReady`/`markUnready`/`isReady`), set once at boot completion, read only inside `GET /health/ready` (503 until set, 200 after — never re-checks DB per request). `GET /health/live` is unconditional 200 once listening, zero dependency checks. Both routes live at `backend/src/infrastructure/routes/health.ts`, mounted at `/health` in `app.js` ahead of CORS/body-parsing. These two endpoints are the only real material for a post-deploy smoke test today.

**Migrations**: Umzug-based (`backend/src/database/migrate.js` + `migrator.js`), a single consolidated baseline (`backend/src/database/migrations/20260724000000-baseline.js`) — the prior 3-SQL-file migration set was already superseded per the archived `schema-migrations` spec (locked in, not to be re-litigated). `checkNoPendingMigrations.js` runs two layers at boot: Umzug bookkeeping (`migrator.pending()`) plus a physical-schema check (`showAllTables`/`describeTable` against a hardcoded 6-table `REQUIRED_SCHEMA` map) — so a bookkeeping-caught-up-but-physically-drifted DB still fails boot. Commands: `db:migrate` (up), `db:migrate:status` (pending), `db:migrate:down` (rollback ONE most-recent migration only, explicitly destructive, no batch rollback), `db:migrate:adopt-baseline` (marks-only, no DDL). The app boot path deliberately refuses to auto-migrate — any deploy pipeline needs its own explicit, ordered migrate step before the new app version starts serving traffic.

**Fail-closed boot guards (`backend/src/app.js`)**: `JWT_SECRET` required outside `NODE_ENV=test` (throws at require-time). `CORS_ORIGIN` required when `NODE_ENV=production` (throws at require-time) — without it, CORS silently falls back to a localhost-only allowlist that would reject every real production origin. Both are require-time throws: the process won't even start without them in production.

**Build/start scripts**: root `package.json` has no build/deploy scripts beyond `frontend:build`. `backend/package.json`: `start` = `node index.js` (respects `RUN_COMPILED`/`NODE_ENV` at runtime), `build` = `tsc -p tsconfig.build.json` (emits `dist/`, excludes tests). `frontend/package.json`: `build` = `astro build`, `preview` = `astro preview`. Documented production start (README/RUNBOOKS): `pnpm --filter backend build`, then run with **both** `RUN_COMPILED=true` and `NODE_ENV=production` set together.

**CI (`.github/workflows/ci.yml`)**: entirely verification-only, zero CD/deploy jobs. Four jobs: `quality` (lint, `architecture:check`, `type-check`, `test:fast`, `test:coverage`, `frontend:check`, `frontend:quality-check`, `frontend:build` with a placeholder `PUBLIC_API_URL`), `integration` (real MySQL 8 service container, migrations then integration tests), `e2e` (Playwright vs MySQL), `verification-gate` (fan-in requiring all three prior jobs green — the one README names as intended for branch protection, "pending explicit maintainer authorization outside this repo"). No job publishes an artifact/image anywhere or targets any environment; `frontend:build`'s CI run explicitly never deploys its output.

**Deploy-platform config**: none exists. No app `Dockerfile` (only an unrelated one inside `node_modules/.pnpm/yaml-language-server`), no `Procfile`, `fly.toml`, `render.yaml`, `vercel.json`, or Kubernetes manifests. The repo-root `docker-compose.yml` only runs a bare `mysql:8.0` container for local/dev convenience (mirrors CI's MySQL service) — it does not package or run the app.

**Env vars**: `backend/.env.example` and `frontend/.env.example` exist per README. Documented backend surface: `PORT` (default 3031), `DB_USER`/`DB_PASS`/`DB_NAME`/`DB_HOST`, `COOKIE_SECRET` (HMAC-signs the double-submit CSRF cookie, required outside tests), `COOKIE_DOMAIN` (optional, empty in dev/CI; must be the root registrable domain in production, e.g. `mundo3d.com`, for `m3d_auth`/`m3d_csrf`/`m3d_user` to be readable across an API subdomain), `JWT_SECRET` (required outside tests), plus `RUN_COMPILED`, `NODE_ENV`, `CORS_ORIGIN`, `SHUTDOWN_TIMEOUT_MS`, `LOG_LEVEL`, `LOGIN_LIMIT_WINDOW`/`MAX`, `REGISTER_LIMIT_WINDOW`/`MAX`. Frontend: `PUBLIC_API_URL` (required at `astro build` time — the build throws if unset, and the value is statically baked into the client bundle, so a wrong build-time value cannot be fixed by a runtime env change post-deploy).

**`docs/RUNBOOKS.md`**: already exists and explicitly states, in both its opening line and its closing "Compiled production start" section, that this repo defines *no hosting platform* — "no Dockerfile, no CI step that installs with --prod and runs the compiled build ... that's the next real gap." It already documents log reading (structured JSON, Pino, auto-redacted auth headers/cookies in production), two boot-failure incident diagnostics (tied to the same boot sequence above), CI red-build triage, a secret-rotation table (`JWT_SECRET`, `COOKIE_SECRET`, `DB_PASS` with blast radius and procedure per secret), and migration-rollback caveats. It is deliberately deploy-target-agnostic and defers platform-specific steps until a target is chosen.

### Affected Areas

- `backend/index.js`, `backend/src/app.js` — boot guards and env-var contract any deploy pipeline must satisfy; no changes anticipated, but the deploy runbook/config must match them exactly.
- `backend/src/infrastructure/health/readinessState.ts`, `backend/src/infrastructure/routes/health.ts` — the only endpoints usable for a post-deploy smoke test today.
- `backend/src/database/migrate.js`, `backend/src/database/checkPendingMigrations.js`, `backend/src/database/migrations/20260724000000-baseline.js` — migration execution must be sequenced explicitly by whatever deploy pipeline is designed; boot will refuse to serve if this step is skipped or misordered.
- `backend/src/infrastructure/middlewares/upload.ts` — `multer.diskStorage` writes to `path.join(process.cwd(), 'public', 'img', dest)` (`backend/public/img/products/`, `backend/public/img/users/`) with `uuidv4()`-based filenames; this is the single most consequential deploy-shape constraint (see below).
- `frontend/astro.config.mjs` — confirms static (SSG) output (`defineConfig({})`, no adapter, no `output` set) and the build-time-required `PUBLIC_API_URL` gate.
- `.github/workflows/ci.yml` — entirely verification-only; any CD job would be new, additive work, not a modification of existing jobs.
- `docker-compose.yml` — dev-only MySQL container; not an app-packaging artifact.
- `docs/RUNBOOKS.md`, `README.md` — both already anticipate a "hosting platform not yet defined" gap and would need deploy-specific sections added once a target is chosen.
- No `Dockerfile`, `Procfile`, `fly.toml`, `render.yaml`, or `vercel.json` exist anywhere in the repo — greenfield for whichever platform is chosen.

### Architecture Facts Relevant to Deploy Choices

- **Backend**: Express + Sequelize + MySQL (`mysql2`), stateful only at the database layer (auth is JWT-in-cookie, no server-side session store) — the app process itself is stateless, but MySQL needs durable, persistent storage independent of app container lifecycle. No background jobs/cron/queues exist anywhere in `backend/src` (confirmed via grep for `setInterval`, `node-cron`, `cron(`, `BullMQ`, `agenda(` — zero matches).
- **Frontend**: Astro 6, default static (SSG) output confirmed by `astro.config.mjs` (`defineConfig({})`, no adapter). Deployable to any static host/CDN, no Node server required for the frontend. `PUBLIC_API_URL` is compiled into the bundle at build time — changing it means a rebuild+redeploy, not a platform-level runtime env var flip.
- **File uploads**: confirmed real local-disk state via `upload.ts` — no object-storage fallback anywhere in code. README's own "Limitaciones actuales" section already names this: "no hay almacenamiento de objetos externo ni persistencia compartida entre instancias" — the maintainers are already aware this breaks multi-instance/ephemeral-container deploys.

### Real Constraints and Open Questions (not decided here)

1. **Target platform is entirely unchosen.** A single VM/VPS keeps local-disk uploads working as-is (persistent disk) but has the least automation and no built-in rollback/zero-downtime tooling. A PaaS (Railway/Render/Fly.io-style) is fast to set up but most tiers have ephemeral app-service filesystems (uploads lost on redeploy/restart unless a paid persistent-volume tier is used), usually pairs with a managed MySQL add-on, and typically supports "redeploy previous build" as its rollback mechanism. Containerizing on a cloud provider (ECS/Cloud Run-style) is the most automatable and scalable but has an ephemeral app filesystem by default, making the uploads problem a hard blocker unless paired with a mounted volume or object storage, and requires building a registry/image pipeline from scratch. Each has different persistent-storage, rollback, and cost/ops tradeoffs — not chosen here.

2. **Multer local-disk uploads are the single most architecturally significant gap** for most container-based targets. Two real resolution paths, each with real consequences: (a) accept local disk + require the platform to provide a persistent/mounted volume for `backend/public/img/` — zero code change, but constrains platform choice and blocks horizontal scaling of the backend (an upload on instance A is invisible to instance B); (b) move to object storage (S3-compatible) — removes the platform constraint and enables horizontal scaling, but is real code work in `upload.ts` plus however served images are read back (currently `express.static` serves `backend/public` directly), a new credential/config surface, and a migration path for already-uploaded files. This decision needs to be made alongside — not after — the platform choice.

3. **MySQL hosting**: co-located with the app (simplest, but couples app/DB lifecycle and scaling, and makes backup/restore the operator's own responsibility) vs. a managed DB service (separate lifecycle, usually built-in automated backups/point-in-time restore, but adds a network hop, its own credential-rotation surface, and typically direct cost). No backup/restore procedure exists in any documented form today.

4. **"Rollback" is not one thing here.** Application-code rollback (redeploy the previous image/build) is comparatively easy and orthogonal to the database. Schema-migration rollback is a fundamentally harder, separate problem: `db:migrate:down` only reverts the single most-recently-applied migration, is explicitly destructive (drops whatever it created), and has no batch/multi-step rollback shortcut (already documented in `docs/RUNBOOKS.md`'s "Rolling back a migration" section). A deploy that ships new code AND a new migration together, then needs to roll back, faces an ordering hazard this repo has no policy on today (e.g. an expand/contract migration discipline) — a genuine open design question for the proposal phase.

5. **No CD job exists at all** — which CI job(s) should gate an actual deploy, and what a post-deploy smoke test concretely checks (the `/health/live` then `/health/ready`-polled-to-200 pattern is the obvious candidate given these are the only production-safe, dependency-aware endpoints that exist today), are both proposal-phase decisions.

### Approaches (deploy-target shapes, illustrative only — not a decision)

1. **Single VM/VPS with persistent local disk** — one machine runs the compiled backend and (optionally) MySQL, both on the VM's persistent disk.
   - Pros: zero code change to uploads; simplest mental model; cheapest at small scale; full control over migrate-then-deploy ordering.
   - Cons: manual/scripted provisioning and patching; no built-in zero-downtime deploy or rollback (must be built, e.g. blue-green via reverse proxy); backend cannot scale horizontally without first solving uploads; single point of failure unless app/DB are deliberately separated.
   - Effort: Low to stand up; Medium to add real zero-downtime/rollback tooling.

2. **PaaS with a persistent volume + managed MySQL add-on** — app on the platform's persistent-disk tier, MySQL as a separate managed service.
   - Pros: fast setup, built-in deploy pipeline (often git-push-to-deploy), platform-managed TLS/networking, "redeploy previous build" rollback usually built in.
   - Cons: persistent-volume tiers cost more and vary in guarantees across providers; still doesn't solve horizontal scaling for uploads (a mounted volume is typically per-instance); managed MySQL add-on pricing/limits vary; less control over exact migrate-then-deploy sequencing.
   - Effort: Low to Medium.

3. **Containerized on a cloud provider + object storage + managed DB** — backend as a container image, uploads moved to S3-compatible storage, MySQL as a managed service.
   - Pros: horizontally scalable from day one; clean separation of stateless app / durable object storage / durable DB; most aligned with conventional production best practice for this shape of app.
   - Cons: requires the `upload.ts` code change (real implementation work); requires a new Dockerfile and image registry/build pipeline (none exist); more moving parts to operate (object-storage IAM, registry, DB networking); highest upfront effort.
   - Effort: High.

### Recommendation

Do not choose a platform in the proposal phase without explicit user input — the three shapes above differ materially in cost, ops burden, and required code changes, and the uploads decision (item 2 above) is coupled to whichever platform is chosen. What IS safe to lock into a proposal regardless of platform: (a) an explicit migrate-then-deploy pipeline ordering (run `db:migrate` as its own gated step before the new app version starts serving traffic — boot already enforces the app-side half of this, but the pipeline needs to own the ordering), (b) a post-deploy smoke test built on the existing `/health/live` + `/health/ready` endpoints, and (c) a consolidated required-in-production env var checklist (already mostly known from README/AGENTS.md, just needs assembling into deploy-specific guidance). Surface the platform choice, the uploads-storage decision, MySQL-hosting choice, and rollback-semantics policy explicitly to the user in the proposal phase.

### Risks

- The multer local-disk upload mechanism is incompatible with any platform whose default app-service filesystem is ephemeral (most container PaaS tiers and most cloud-container setups) — deploying without addressing this first means uploaded product/user images silently vanish on the next redeploy or restart. Highest-severity gap found.
- Schema-migration rollback and app-code rollback are two different operations with no documented interaction policy; a deploy shipping incompatible app+migration changes together has no safe, tested rollback path today (`db:migrate:down` is manual, destructive, one-step-at-a-time).
- `CORS_ORIGIN` and `JWT_SECRET` are already fail-closed at require-time in production — a deploy pipeline MUST supply them or the process won't start at all (a safety benefit, but must be reflected in whatever env checklist the proposal produces).
- No confirmed branch-protection/required-check policy exists on `main` yet (README: "pending explicit maintainer authorization outside this repo") — a CI-gated deploy pipeline needs that resolved too, though it's out of scope for this exploration.
- The `design.md` referenced in code comments (source of the "compiled production entry point" and "forced-shutdown timeout is env-configurable" decisions) could not be located anywhere in the current tree — likely lives only in an already-archived/removed SDD change folder; its rationale had to be reconstructed from comments and `openspec/specs/runtime-resilience/spec.md` instead.
